# FalconGEMM 布局与选择性融合实验，2026-10-15

用户授权范围：尝试协调 S/T 布局与供数，以及选择性融合。仅测 H100 / 1024³ / BF16、FP16 / FP32 输出。FP8 残差修正保持停止；没有修改原始输入 FP64 参考、精度门槛或 Auto=Dense。

结论：完成两个方向的实现、完整调用比较和独立验证，没有形成值得替换基线的性能收益。按行交错只有约0.1%–0.8%的小正向信号；细粒度交错使普通FP16变慢；片上S3/T3差分大幅变慢。最终 iter336 从 `6d4167b` 逐字恢复整个 solution，即实验前 iter330。当前 SW 仍未通过原始精度门槛。更广泛的精度/性能研究目标未完成。

## 实现与来源

参考论文：FalconGEMM v4，https://arxiv.org/html/2605.06057v4 ，III-B讨论分组数据复用、调度及融合边界。本文所有数字来自本仓库独立实验，不是论文数字。

| 迭代 | 源码提交 | 改动 |
|---|---|---|
|331|6d4167b|实验前源码的新测基线；当前源码来自iter330|
|332|e4dd218|S/T分别按行交错四个平面，更新变换存储地址与TMA strides；算术、shared布局、同步均不变|
|333|28b4344|S/T四平面按64元素、128字节条带交错；T使用4D tensor map，保持原GMMA shared布局|
|334|b762d58|片上S3/T3首原型，scratch swizzle起始相位不匹配，输出错误；全部计时无效|
|335|35817d1|修正scratch位置，在计算CTA内形成S3=A11-A21、T3=B22-B12；主变换不再写这两个平面|
|336|da8bf87|从331提交逐字恢复整个solution，重新构建与完整计时|

候选335复用原有空闲生产侧warps处理差分，增加一个24KiB暂存区、raw TMA完成barrier、shared async proxy fence、128线程named barrier，然后发布原ready barrier。原七个乘积的次序、WGMMA累加与FP32重组不变。workspace维持4MiB，未用的S3/T3平面留空；真实写回从4MiB降到3MiB，shared从196736增到221440字节。

334的scratch放在ready/free之后，较操作数起始地址偏移128字节，两次TMA swizzle的物理元素位置不匹配。335将scratch移到barrier数组之前，使起始地址落在相同1024字节相位，随后逐位检查通过。这是原型实现错误的修正；334不能用于评估正确融合方案的性能。

## 原始精度与独立实现验证

三个正确候选332/333/335在原benchmark三轮fresh-input上均保持基线误差：BF16最大eF约0.00601519652935、FP16约0.000754625769821，无nonfinite。门槛仍分别约0.00100256、0.00010375，全部FAIL。进程exit2来自数值门槛失败，未被当作PASS或静默忽略。

- 332、333、335各自通过72项与331独立编译源码的逐位对照：两种dtype、六类输入、每类三个新数据集、普通与Graph。输入包括均匀、抵消、动态范围、小数、全零、稀疏；输出均有限。
- 335另外通过CUDA12.8 compute-sanitizer的quick memcheck、racecheck、synccheck，全部0 errors、racecheck 0 warnings。
- 335通过256次双stream/Graph调用，独立workspace每次poison，最终输出与基线逐位相同。
- 332/333没有改变同步协议；未对这两个被拒绝的布局候选额外运行sanitizer或双stream检查，不将335的检查转用于它们。

上述实现等价验证不代表通过原始FP64数学验收。

## Profiling与成本解释

同轮NCU，`--profile`、每个版本捕获两种dtype共4个kernel，cache-control none、clock-control none。选择相同metrics，全部捕获成功、数值非NaN。原始CSV在 `profile/`，精简结果在 `profile/summary.json`。NCU采集窗口、PDL重叠、输入轮换方式与正式计时有差异，计数器用于诊断；不把回放时间用作完整调用速度，不把全局L2计数唯一归因于某条指令或具体L2 bank。

|版本|BF16计算指令数|FP16计算指令数|计算寄存器/线程|动态local读写sector|
|---|---:|---:|---:|---:|
|331|1267072|1267985|60|0|
|332|1267072|1267896|60|0|
|333|1271168|1272215|60|0|
|335|2760320|2170496|64|0|

332的变换指令比331每种dtype少2048条，计算指令基本不变。没有观察到L2请求显著减少：同一计算采集窗口BF16读sector约1.490M→1.497M，FP16约1.464M→1.465M。这与完整调用只有小变化相符，不能证明更接近的平面就必然减少实际请求。

335的变换阶段指令减少，但计算阶段指令大增；采集窗口L2读sector BF16约1.817M、FP16约1.786M；long-scoreboard占活跃warp比例约49%，基线约19%/17%。这些现象共同表明额外供数、片上差分和协调有较高成本，没有证据支持spill归因。不能把某一项计数独自解释成全部延迟增加。

独立于计数器的逻辑数据量模型也不利：每CTA TMA copy从56增到64；原七乘计算的逻辑TMA payload约84MiB/调用，新版约96MiB/调用，因为P7必须载入两份原始操作数再相减。省去1MiB变换写回，同时增加约12MiB计算侧逻辑载入。这是CTA层面的请求payload估计，不等于HBM物理流量；缓存可能合并/复用请求。

因此，本次选择性融合没有实现跨CTA复用原始输入，反而增加了计算CTA中的重复工作。该结果仅否定这一个S3/T3融合实现，不是对所有选择性融合的下界证明，也不支持重新开启已停止的FP8补偿路线。
