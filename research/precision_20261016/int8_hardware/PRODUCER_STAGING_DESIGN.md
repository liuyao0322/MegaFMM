# Shared staging after the two-plane producer profile

P21 measured A254/B132 registers for balanced BF16, with zero local sectors on the profiled normal input. Input L2 reads fell about31%/29% versusP20, but full calls improve only1–2%. B exceeds the128-register allocation threshold for two256-thread CTAs on the H100 SM; input reuse did not create more resident CTAs. This is a resource hypothesis, not a measured occupancy benefit.

The next producer-only experiment retains P24's measured consumer and all numerical operations. Store the two transformed FP32 planes in software-managed shared memory, keep the existing shared high reduction and B transpose, and bound all producer loop unrolling to1. After maxima selection, reload a plane, repeat the same dtype cast/residual and quantization, write exactly the same native/INT8 layouts. Do not keep four quadrants or additional high/low arrays in registers. Native and integer consumer math, per-column inside scales and quantization tiles remain unchanged.

Shared storage is65576bytes forA and42020bytes forB, subject to actual sizeof/compiler allocation. A exceeds the default static48KiB, so use dynamic shared storage with explicit cudaFuncSetAttribute during init, outside timed run and Graph capture. Two independent A/B launches remain for this controlled experiment. This may trade register pressure/instruction-cache footprint for extra shared traffic and synchronization; no speed conclusion before a full build and original-input FP64 timing run.

Source generation is in generate_shared_packer.py and must start from a frozen measured candidate with78passing checks. It changes only producer storage/unrolling, matching dynamic launch sizes and init attributes. C7515, actual stack/spills, register usage,78checks,79,872exact inside exponents and printed-eF equality to the frozen base must be inspected. All actual preparation/encoding/compute costs remain in full-call timings. A retained producer needs its own Graph/dual-stream/scoped sanitizer checks, even if its base consumer was validated.

Resource basis: [NVIDIA CUDA Best Practices](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html) discusses register/shared-resource occupancy limits and the non-monotone relationship between occupancy and speed. Software staging is implemented explicitly in CUDA12.4; no CUDA13 compiler spill feature or toolchain installation is assumed.
