# P30: one complete exact exponent reduction per CTA

P29's own ordinary ABBA improves3.97/3.58percent but its separateGraph ABBA regresses6.45/6.99percent versusP27. This is a measured call-mode tradeoff, not proof that either grid barrier alone causes the regression. P30 tests removing the partial/finalize phase boundary while preserving exact per-column inside scaling. It starts from frozenP29, keeping joint pack, consumer, all seven native products/eight integer dots, quantization and workspace offsets unchanged.

The cooperative launch still has288CTAs of256threads. Only the first128CTAs reduce inputs; blockb owns the eight columns k=8*b..8*b+7. ForA, tid%8 selects the column and tid/8 the initial row; row+=32 covers all1024rows. Within each warp, xor8 andxor16 combine the four row groups sharing a column. Lanes0..7 write one maximum per warp/column into64shared floats. ForB, warp0..7 owns one Krow, lane0..31 iterates columns withstride32 and performs a warp maximum. Lane0 writes one of8shared floats. After a block barrier, threads0..7 combine the eight A warp maxima and their B maximum, then run the original log2/round-to-nearest exponent formula. Each column sees exactly the original input elements; maxima over finite absolute values do not depend on reduction order.

All288CTAs, including the160inactive reduction blocks, execute one unconditionalgrid.sync. Only afterward may any CTA read inside exponents or reuse scratch for the unchanged joint pack. The partial workspace and unused kernel parameter are preserved; no input cache, allocation or host synchronization is added to run. Actual cooperative support/occupancy checks remain in init. The altered kernel needs its own ordinary78checks, exact79,872exponents, Graph, independent fresh dual-stream guard checks and scoped sanitizers; P29's results do not transfer.

This halves the useful A bytes per sector compared with32byte-aligned16element FP16/BF16 column segments, uses only128active reductionCTAs and increases each thread's serial reduction length. Removing a barrier/partial traffic need not improve either full ordinary orGraph latency. A later K16/64CTA variant would be another coalescing/parallelism tradeoff, not an assumed improvement. Performance and retention must be recorded from actual completed measurements inEXPERIMENTS.md.

Cooperative grid ordering and capacity requirements follow the [CUDA12.4 grid synchronization guide](https://docs.nvidia.com/cuda/archive/12.4.0/cuda-c-programming-guide/index.html#grid-synchronization) and [launch API contract](https://docs.nvidia.com/cuda/archive/12.4.0/cuda-runtime-api/group__CUDART__EXECUTION.html). These establish implementation constraints, not a speed prediction.
